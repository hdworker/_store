# Процесс разработки 1С (сервер)

Единое описание: хранилище, репозитории, сборка, запуск и проверка.
Дополняет `AGENTS.md` (глобальные правила) и `_store\README.md` (правила хранилища).

## Источники правды

| Что | Где |
|---|---|
| Базы, v8path, default | `_store\.v8-project.json` |
| Эталон XML конфигурации | `_store\reference\config\<ИмяКонфигурации>_<Версия>` (read-only) |
| Эталон XML расширений | `_store\reference\extensions\<Имя>\<Версия>` (read-only) |
| Вендорские CFE | `_store\vendor\extensions` |
| CF/CFE сборки конфигурации | `_store\vendor\config` (для развёртывания с нуля) |
| Опубликованные сборки | `_store\extensions\<Имя>\<X.Y.Z>\<Имя>_v<X.Y.Z>.cfe` (create-only) |
| Исходники расширения | `<Проект>\src\cfe\<Имя>` (git проекта) |
| Сборки проекта | `<Проект>\build` |
| Чек-листы | `<Проект>\checks` |

## Поток

1. Правка XML в `src\cfe\<Имя>` (эталоны — в `_store\reference`; типовую не меняем).
2. Сборка CFE: `db-load-xml` (свободная база) → `db-update` → `db-dump-cf` → `build`.
3. Загрузка/применение в тестовую базу: `db-load-xml` → `db-update -Dynamic on`.
4. Публикация: `_store\extensions` — create-only, имя `<Имя>_v<X.Y.Z>.cfe`, бронь `current.json`.
5. Проверка: `1c-check-task` (preflight + запуск, `-Deep` — применимость и версия в базе).

Правила версий: `<Version>` в `Configuration.xml` = суффикс CFE; каждая сборка — инкремент.
Префиксы расширений в базе уникальны; на метод — не более одного `&Вместо`.

## Реквизиты — только кодом (типовой механизм)

Реквизиты форм создаются **программно**: `Новый РеквизитФормы` + `ИзменитьРеквизиты`
(и, при необходимости, элемент через `Элементы.Вставить`/`Элементы.Добавить`).
Руками в Конфигураторе — нельзя.

**DFI не подключаем.** `ДФИ.СоздатьРеквизит()`/`СоздатьРеквизиты()` — тонкая обёртка над тем же
типовым механизмом; ради одного реквизита тянуть общий модуль `ДФИ` (весь `ModuleDFI.bsl`)
нецелесообразно. Решение зафиксировано по опыту независимого агента (использовал типовую
функциональность напрямую).

Рабочий пример из доработки:

```bsl
&НаСервере
Процедура бкк_ДобавитьРеквизитВремяДоВвода()
	
	Если Элементы.Найти("бкк_ВремяДоВвода") <> Неопределено Тогда
		Возврат;
	КонецЕсли;
	
	ДобавляемыеРеквизиты = Новый Массив;
	ДобавляемыеРеквизиты.Добавить(
		Новый РеквизитФормы(
			"бкк_ВремяДоВвода",
			Новый ОписаниеТипов("Строка"),
			"",
			"Время до ввода",
			Ложь));
	
	ИзменитьРеквизиты(ДобавляемыеРеквизиты);
	
	Эл = Элементы.Вставить("бкк_ВремяДоВвода", Тип("ПолеФормы"), Элементы.ГруппаШапкаПраво, Элементы.ГруппаСообщенияКоманды);
	Эл.Вид = ВидПоляФормы.ПолеНадписи;
	Эл.ПутьКДанным = "бкк_ВремяДоВвода";
	Эл.Заголовок = "Время до ввода";
	
КонецПроцедуры
```

Сигнатура: `РеквизитФормы(Имя, ОписаниеТипов, Путь = "", Заголовок = "", ТолькоПросмотр = Ложь)`.

## Общие функции между расширениями

В 1С расширения **изолированы**: одно расширение не может вызывать общий модуль другого
расширения. Поэтому «общее расширение-библиотека», на которое ссылаются остальные, технически
невозможно.

Рабочий способ — «вендоринг модуля»:

1. Канонический текст модуля хранится в `_store\vendor\libs\<Имя>\<Версия>\`.
2. Каждое расширение, которому нужны функции, включает **свою копию** этого модуля
   (например, общий модуль `бкк_Общие`), вызывая только его.
3. Копии синхронизируются из стора; версия копии фиксируется в `store-index.json`.
4. В библиотеку попадают только функции с реальным переиспользованием (≥2 расширения).

Дублирование кода между расширениями в этом случае — следствие изоляции платформы, а не ошибка.
Пока общих функций мало, отдельную библиотеку не заводим: дублируем по месту.

## Запуск операций (без ожидания оболочки)

**Основной способ — MCP-сервер `cc`** (stdio, зарегистрирован в `opencode.jsonc`):

| Инструмент | Назначение |
|---|---|
| `run_start(script, args?, cwd?)` | detached-запуск `.py` из `skills`; сразу `run_id/pid/out` |
| `run_status(run_id)` | `state` (`run|done|fail|stale`), exit, длительность, последняя строка |
| `run_tail(run_id, offset?)` | новые байты `out.log` с offset (стриминг) |
| `run_wait(run_id, timeout_sec?)` | ожидание завершения (по умолчанию 60 с, максимум 600 с; таймаут не отменяет запуск) |
| `run_kill(run_id)` / `run_list(limit?)` | прерывание / список запусков |

### Таймауты и задержки в скриптах

- MCP `run_wait`: по умолчанию 60 с, жёсткий предел 600 с, проверка состояния каждые 0,5 с. По таймауту возвращается текущий статус с подсказкой продолжить `run_status/run_tail`; сам процесс остаётся запущен.
- CLI `async_run.py wait`: по умолчанию 300 с, опрос каждые 2 с; окончание времени ожидания также не останавливает процесс.
- Очередь `queue.py`: дедлайн выполнения одного запроса по умолчанию 60 мин; максимум 8 запусков. Если запуск завершился с сообщением о блокировке, задержки перед следующими запусками — 2, 5, 10, 15, 30, 30, 30 мин. Если до запуска обнаружен Конфигуратор/активный async-процесс, preflight назначает ожидание по текущему счётчику `attempts` (при `attempts=0` — 1 мин), но сам счётчик не увеличивает: до освобождения базы повторяется та же задержка; после неудачного запуска с блокировкой используется интервал соответствующего текущего счётчика.
- Воркер очереди проверяет ожидающие запросы раз в 5 с; список процессов Конфигуратора кэшируется на 30 с, сама PowerShell-проверка имеет timeout 90 с. Поэтому `next_try` — не точная гарантия старта в эту секунду.
- `p.wait(timeout=0.5)` в db-скриптах — частота проверки завершения процесса для вывода лога, а не лимит длительности операции.

Эти ожидания/опросы не являются временем отклика ИБ и не должны включаться в замер её производительности.

Замеры (задача ~3 с): отклик direct 3.07 s → async_run 0.22 s → **MCP 0.15 s**;
стоимость опроса: CLI `async_run status` ~207 мс против **MCP ~7 мс**.

**Fallback без MCP:** `python skills\_shared\async_run.py start -- python "<скрипт>" ...`
(+ `status/tail/list/wait`), данные те же.

`run_start` принимает `.py` из `skills` **и из агентской temp-зоны** (`%TEMP%\*\opencode\*.py`) —
сравнения, публикации и прочие скрипты агента тоже запускаются без ожидания bash.

**Монитор для человека:** `python skills\_shared\cc-status.py` — живой дашборд
(секции «В ПРОЦЕССЕ»/«ЗАВЕРШЁННЫЕ», прогресс по медиане, лог выбранной операции).

## Очередь операций (cc_queue)

Если база занята (Конфигуратор, фоновые задания, параллельные запуски) — запрос кладётся в
очередь: MCP `queue_submit(script, args, cwd, base, expect_config?, expect_extensions?, priority?)`
мгновенно возвращает `queue_id`, а исполнение произойдёт автоматически, когда база освободится.

- Запросы: `%LOCALAPPDATA%\cc_queue\<id>` — `request.json`, `state.json`, `out.log`, `exit.code`.
- Состояния: `pending → waiting-lock → running → done | failed | blocked-version | expired | cancelled`.
- Воркер: один на машину (`skills\_shared\queue.py worker`, поднимается сам при submit);
  FIFO внутри базы, параллельно по разным базам. Точные сроки, дедлайн и различие между
  preflight-занятостью и повтором после ошибки — в разделе «Таймауты и задержки в скриптах» выше.
- Версии: `_store\bases\<ref>.json` (профиль: config, version, extensions). Несовпадение с
  `expect` → `blocked-version` **без запуска** (код писался под другую версию базы).
  Профиль заполняется: `queue.py profile -Ref test1 -Config "<Имя>" -Version 2.5.17.219`;
  нет профиля — проверка версии пропускается.
- CLI: `queue.py add|status|list|cancel|worker|once|profile`.
- Видно в мониторе: `cc-status.py` — секция **«⏳ ОЧЕРЕДЬ»** и счётчик в шапке.

## MCP-мост к живой базе (1c-local-bridge)

Для **получения информации из базы** (запросы, выражения, метаданные) используется MCP-сервер
**`1c-local-bridge`** (`E:\Grishin\mcp-1c-local-bridge`, зарегистрирован в `opencode.jsonc`) —
это замена COM-соединению: работает через открытый сеанс 1С пользователя, промежуточного сервера нет.

- Запуск: открыть в базе `dist\MCPLocalBridge.epf` («Файл — Открыть»); пока форма открыта — сеанс жив.
- Инструменты: `sessions`, `ping`, `query` (запрос + параметры), `eval` (`Вычислить`),
  `execute` (`Выполнить`, результат в `Результат`), `metadata` (состав/описание объекта), `result`, `cancel`.
- Безопасность: серверный код по умолчанию в транзакции с откатом (изменения не сохраняются);
  запись — только `allow_write=true` + разрешение «Запись в базу» на форме; пока команда идёт,
  окно 1С занято; ответы >20 000 символов — в `~/.cache/mcp-1c-local-bridge/results/`.
- Обмен: `%TEMP%\mcp-1c-local-bridge` (свой каталог — `MCP_1C_BRIDGE_DIR` + «Каталог обмена» на форме).
- Правило: **чтение базы — через `1c-local-bridge`**, а не COM-соединением; изменения данных —
  только через наши операции (`db-*`/CFE) с обычным контролем.

## Инструменты процесса

- `1c-init` — новый проект/расширение: свободная база, `.v8-project.json`, заготовка;
  `-Adopt` — подключить существующий проект к стору (ничего не удаляет).
- `1c-check-task` — preflight + запуск клиента в согласованной базе.
- `cc-status.py` — наблюдение за всеми запусками (в т.ч. других сессий).

## Технические правила

- **Перед сборкой CFE — просмотреть [`FINAL-CHECKS.md`](FINAL-CHECKS.md)**: типичные ошибки
  (например, «Неоднозначное поле "Товары.Ссылка"» — уникальные псевдонимы и полная
  квалификация полей в запросах) и быстрый чек-лист.
- **Не использовать bash для поиска/сравнения/копирования**: поиск — нативный Grep, чтение — Read
  (0.0–0.2 с), файловые операции и скрипты — Python через MCP. Bash стоит 60–180 с на вызов
  (та же картина в сессиях: `grep` 90 с, `diff` 120 с, `cp` 180 с при работающем MCP).
- Файлы — UTF-8; PowerShell/консоль портят кириллицу — предпочитать Python.
- Пароли в выводе маскируются (`-Password ***`); единственный реестр учётных данных — `_store\.v8-project.json`.
  Не передавать пароль в аргументах `queue.py`: запрос сохраняет `args` в `request.json`; `async_run.py`
  также сохраняет команду в `cmd.txt`. Использовать безопасное разрешение секрета из реестра в памяти,
  не печатая и не сохраняя его.
- Долгие операции не ждать синхронно: `run_start` → `run_tail/run_status`; `run_wait` ограничивает
  только время ожидания (максимум 600 с), не длительность и не жизнь фонового процесса.
- `LoadConfigFromFiles`/`UpdateDBCfg` требуют свободы от Конфигуратора; фоновые задания
  могут давать «Ошибку исключительной блокировки» — повторить позже.
